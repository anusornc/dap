# Plan: Semantic Layer for DAP — PROV-O + SHACL + Semantic Agent Cards

## Status

**Planning phase** — not yet implemented. This doc defines the approach before execution.

---

## Problem Statement

DAP has working message routing, job queuing, and TLS — but it lacks:

| Gap | Impact |
|-----|--------|
| **No provenance tracking** | Can't trace where a message came from, who handled it, or why a job was delegated |
| **No formal capability registry** | Agents describe themselves with freeform strings; no semantic matching |
| **No message schema validation** | Current validation is basic JSON structure only |
| **No Agent Cards** | SOTA protocols (A2A, ANP) use self-describing agent manifests for discovery |
| **No audit trail** | Job history is stored but not linked to the agents that produced/consumed data |

**Project score stays at 7.5/10** until these are addressed — they were the exact SOTA gaps identified earlier.

## Research Findings

### PROV-O (W3C Standard)

The W3C Provenance Ontology models provenance as three interacting primitives:

```
Entity          → things (messages, data, documents)
Activity        → actions (processing, routing, transformation)
Agent           → actors (agents, humans, software systems)
```

Key relationships map naturally to DAP:

| PROV-O Term | Maps to DAP |
|------------|-------------|
| `prov:used` | Agent consumed input data |
| `prov:wasGeneratedBy` | Entity generated by an Activity |
| `prov:wasAssociatedWith` | Agent performed an Activity |
| `prov:wasAttributedTo` | Entity traced to responsible Agent |
| `prov:actedOnBehalfOf` | Delegation chain (parent → child agent) |
| `prov:wasDerivedFrom` | Job result derived from job input |

### PROV-AGENT (August 2025 — NEW)

> *"PROV-AGENT: Unified Provenance for Tracking AI Agent Interactions in Agentic Workflows"*
> — Souza et al., IEEE eScience 2025 ([arXiv:2508.02866](https://arxiv.org/abs/2508.02866))

This paper directly addresses the agent provenance problem. Key takeaways:

1. **Extends PROV-O for LLM/AI agents** with new vocabulary for:
   - Prompts and responses as first-class `prov:Entity`
   - Model invocations as `prov:Activity`
   - Tool calls linked to agent activities

2. **Integrates with MCP** (Model Context Protocol) — same abstraction level as DAP's shim adapters

3. **Enables provenance queries**:
   - "Why did Agent X produce this output?"
   - "What happened to this job end-to-end?"
   - "Root-cause tracing through the agent chain"
   - Hallucination detection (compare outputs against domain constraints)

4. **Cross-environment support**: edge, cloud, HPC — maps cleanly to DAP's cross-machine relay

### SHACL (W3C Standard)

Shapes Constraint Language validates RDF data against declarative schemas. Perfect for DAP because:

- **Define shapes once, validate everywhere** — agents, messages, jobs, agent cards
- **Three severity levels**: Violation (reject), Warning (flag), Info (suggest)
- **Rich constraint types**: datatypes, ranges, patterns, cardinality, logical operators (`sh:and`, `sh:or`, `sh:not`)
- **Actionable error messages**: tells exactly which field failed and why
- **Extensible via SPARQL** for complex cross-field rules

Example — validate that all agents register with valid capability URIs:
```turtle
:AgentShape a sh:NodeShape ;
  sh:targetClass :RegisteredAgent ;
  sh:property [
    sh:path :capability ;
    sh:minCount 1 ;
    sh:message "Agent must declare at least one capability" ;
  ] ;
  sh:property [
    sh:path :capability ;
    sh:nodeKind sh:IRI ;
    sh:message "Capability must be a valid IRI" ;
  ] .
```

### Semantic Agent Cards (ANP/ADP)

Agent Network Protocol (ANP) uses JSON-LD + schema.org + W3C DIDs for agent self-description. This bridges the **Agent Cards gap** from the SOTA analysis.

An Agent Card in JSON-LD:
```json
{
  "@context": ["https://schema.org/", "https://agent-network-protocol.com/"],
  "type": "Agent",
  "name": "DAP-Mavis",
  "description": "Mavis agent for Faculty MIS coordination",
  "version": "1.0.0",
  "skills": [{
    "type": "Offer",
    "name": "code-generation",
    "inputSchema": { "type": "object", "properties": {...} },
    "outputSchema": { "type": "object", "properties": {...} }
  }],
  "protocols": ["dap://", "wss://"],
  "authentication": ["api-key", "did:wba"],
  "metadata": {
    "trustLevel": "verified",
    "prov:wasAttributedTo": "did:wba:faculty-mavis-001"
  }
}
```

## Proposed Architecture

### Layer 1: Provenance Graph (PROV-O)

Every DAP interaction is recorded as provenance triples. Storage is JSON-LD (no RDF triple store needed for MVP).

**Core mapping:**

```
DAP Message          → prov:Entity
DAP Job (Activity)    → prov:Activity
DAP Agent             → prov:Agent
Job submission        → prov:wasGeneratedBy
Job completion        → prov:used + prov:wasDerivedFrom
Delegation            → prov:actedOnBehalfOf
Agent registration    → prov:wasAssociatedWith
```

**Example provenance record:**
```json
{
  "@type": "prov:Activity",
  "prov:label": "job-execution",
  "prov:used": { "@id": "msg:abc123" },
  "prov:wasAssociatedWith": { "@id": "agent:mavis" },
  "prov:generated": { "@id": "entity:result-456" },
  "prov:endedAtTime": "2026-05-21T19:00:00Z",
  "dap:jobId": "job-789",
  "dap:capabilityUsed": "code-generation"
}
```

### Layer 2: SHACL Validation Shapes

**Three shape files:**

| File | Validates |
|------|-----------|
| `shapes/agent-shape.ttl` | Agent registration, capabilities, version |
| `shapes/message-shape.ttl` | DAP message structure and required fields |
| `shapes/job-shape.ttl` | Job metadata, priority ranges, payload constraints |

**Validation timing:**
- **Registration** — validate Agent Card on connect (reject invalid)
- **Messages** — validate on receive before routing (reject malformed)
- **Jobs** — validate on submit (reject non-conforming metadata)
- **Optional**: batch validation endpoint for external audit

**Tool choice:** Use `pyshacl` (Python) or `rdf4j-shacl` (JVM) for Node.js integration. For Node.js-native, use `rdf-ext` + `shacl-playground` JS port, or call a sidecar Python process.

### Layer 3: Semantic Agent Cards

Replace the current freeform capability array with JSON-LD Agent Cards.

**Agent Card endpoint:** `GET /agents/{agentId}/card`
**Well-known endpoint:** `GET /.well-known/agent.json`

**Discovery flow:**
1. Agent connects → sends JSON-LD Agent Card
2. Relay validates Card against `agent-shape.ttl` (SHACL)
3. Card stored in agent registry with full semantics
4. Capability queries use SPARQL-like matching instead of string matching

**Example capability query:**
```
"Find all agents that can do code-generation with TypeScript"
→ SPARQL: SELECT agent WHERE agent.capability CONTAINS "code-generation" 
          AND agent.language CONTAINS "TypeScript"
```

### Layer 4: Integrated Message Flow

```
Agent connects
    ↓
1. Sends JSON-LD Agent Card
    ↓
2. SHACL validates against agent-shape.ttl
    → FAIL: reject with ValidationReport
    → PASS: continue
    ↓
3. Register Agent + generate provenance record
    prov:Agent(mavis) → prov:wasAssociatedWith → RegistrationActivity
    ↓
4. Message exchange creates provenance chain
    Agent A sends Message
    → prov:Entity(message) prov:wasAttributedTo agent:A
    → routed to Agent B
    → prov:Activity(routing) prov:used message
    → prov:wasInformedBy message
    ↓
5. Job submission
    → prov:Activity(job-submit) 
    → prov:wasGeneratedBy job-entity
    → prov:wasAssociatedWith submitter-agent
    ↓
6. Job completion
    → prov:Activity(job-complete)
    → prov:used job-input
    → prov:generated result-entity
    → prov:wasDerivedFrom job-input
    → prov:wasAttributedTo worker-agent
```

## Implementation Approach

### Option A: Full RDF Stack (Heavy)

**Pros:**
- Full PROV-O reasoning and inference
- SPARQL queries for complex provenance
- Best interoperability with academic/scientific tools
- PROV-AGENT compatible

**Cons:**
- Adds RDF4J/Jena dependency (large)
- Triple store setup required
- Higher complexity for agent shim adapters
- Performance overhead for message-level tracking

**Best for:** Research/academic projects, scientific workflows (like PROV-AGENT)

### Option B: JSON-LD Only (Lightweight) ⭐ Recommended

**Pros:**
- No triple store — JSON-LD is just JSON with `@context`
- Easy for Node.js agents (parse as JSON)
- SHACL validation via `pyshacl` CLI sidecar
- PROV-O vocabulary imported as JSON-LD context
- Can upgrade to full RDF later if needed

**Cons:**
- No native SPARQL (can simulate with JSONPath/JSONQuery)
- Reasoning requires external tool

**Best for:** Production DAP, practical multi-agent systems

### Option C: Hybrid (JSON-LD + SQLite provenance)

**Pros:**
- Provenance stored as structured JSON-LD in SQLite
- SHACL validation via sidecar process
- Fast enough for message-level tracking
- Compatible with future RDF migration

**Cons:**
- More moving parts

## Recommended Implementation Path

**Phase 1 — Provenance (Option B):**
1. Define `dap-prov` JSON-LD context (PROV-O subset)
2. Add provenance field to job records: `prov:Activity` structure per job
3. Auto-generate provenance for: registration, job submit, job claim, job complete
4. Store in job persistence (extend `data/jobs.json`)

**Phase 2 — SHACL Validation:**
1. Create three `.ttl` shape files
2. Add `shapes/` directory to project
3. Integrate `pyshacl` for validation (run as pre-commit check or server hook)
4. Expose validation endpoint: `POST /validate` (accepts JSON, returns SHACL report)

**Phase 3 — Semantic Agent Cards:**
1. Define DAP Agent Card JSON-LD schema
2. Add Agent Card endpoint to REST handler
3. Replace freeform capabilities with structured skills
4. Add capability query endpoint: `GET /agents?capability=X`

**Phase 4 — Provenance Query API (optional):**
1. Add query endpoint for provenance chains
2. Implement root-cause query ("trace this job back")
3. Export provenance as standard PROV-JSON for PROV-AGENT compatibility

## Constraints & Assumptions

- **Node.js only** — no RDF4J/Jena dependencies
- **Backward compatible** — existing JSON messages still work, only extended with `@context`
- **Performance** — SHACL validation only on write (not every read)
- **No triple store for MVP** — JSON-LD stored as files, validated via `pyshacl` CLI
- **User has Python** — `pyshacl` pip package used for validation
